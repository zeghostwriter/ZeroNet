# Codebase audit and overhaul — September 2026

Scope: every crate in the workspace (about 92k lines, `reference/` excluded).
The audit ran subsystem by subsystem, looking for real bugs first, then
hot-path cost, network efficiency, stability, and TUI quality. Every fix
below has a test unless marked otherwise.

## Verification

| Check | Result |
|---|---|
| `cargo fmt --all -- --check` | clean |
| `cargo clippy --workspace --all-targets -D warnings` | clean (was ~35 warnings) |
| `cargo test --workspace --all-targets` | 1178 passed, 0 failed (~1000 at baseline) |
| `cargo test --workspace --doc` | all pass |
| Pinned Xray 26.7.28 differential oracle (`--ignored`) | 25/25: protocol interop, VLESS Encryption, XHTTP, TLS fingerprint, DNS, routing, throughput |
| Fuzzing (`cargo +nightly fuzz`, 60 s per target) | ~16.5 M runs across the four parsers, no crashes |
| TUI driven in a real pty (tmux) | every page redraws identically to a forced full redraw |

## Findings and fixes by subsystem

### Security / TLS / REALITY (`zero-security`)
- **REALITY man-in-the-middle bypass.** The CertificateVerify signature was
  only checked for Ed25519; any other algorithm completed the handshake. A
  relay could forward our hello, pass back the real certificate, and finish
  with its own key share. The certificate's key is now the one verified.
- KeyUpdate reply was sealed under the new key (RFC 8446 §4.6.3 needs the old).
- Unbounded write buffering behind a slow peer; now capped at four records.
- Split ClientHello (our own `tlshello` fragmentation) was rejected by the
  REALITY server; now reassembled up to 64 KiB, as Go's server does.
- Non-TLS probes were dropped instead of falling back to the decoy target.
- Constant-time comparisons for Finished, certificate HMAC and shortIds;
  key material zeroized; nonce sequence can no longer wrap.
- In-place record seal/open (was 3 allocations per sealed record).
- Rustls server config rebuilt per connection (so resumption never worked);
  now cached. Client config cache bounded (ECH lists rotate hourly).
- uTLS: padding extension could be shuffled off the end; `fingerprint:
  random` never shuffled.

### Evasion (`zero-evasion`)
- A fragment length of 0 looped forever allocating.
- Keepalive re-created its timer on every pending read.
- Noise drew one RNG call per byte; raw socket leaked on a build error.

### Transports (`zero-transport`)
- **Remote crash:** XHTTP chunk size from the peer went straight into
  `vec![0; n]`; one line aborted the process before auth.
- **Remote crash:** Hysteria2 UDP datagram address bounds check measured the
  wrong length.
- Quadratic header scanning (pre-auth CPU DoS by dripping one byte at a time)
  in XHTTP, HTTPUpgrade and WebSocket.
- Hysteria2/TUIC accepted inline with no timeout: one client stalled the
  inbound, and only the first stream per connection was served.
- **gRPC served only the first stream of each HTTP/2 connection.** Xray
  clients open one stream per tunnel on a shared connection, so every tunnel
  after the first was reset. `grpc::accept_multi` now serves all of them.
- Half-close never reached the app in almost every carrier (connections hung
  until the app closed them); one direction failing did not tear down the
  other.
- XHTTP-over-HTTP/3 packet-up server was wired backwards and carried nothing.
- WebSocket: masking 8 bytes at a time, zero-copy frames, close handshake.
- QUIC receive windows raised (8 MB stream / 20 MB connection); the defaults
  cap a single stream on long links.

### Protocols (`zero-protocol`)
- Shared read/write buffers for Shadowsocks, SS2022, VMess and AnyTLS:
  frames are decrypted in place, one read can yield several frames, and the
  steady state allocates nothing.
- Bounded two-generation replay filter for the server handshakes.
- Mux: a stalled session no longer blocks the whole carrier (reset after 5 s),
  frames are coalesced into one write, idle carriers close like Xray's client.

### Runtime (`zero-runtime`)
- Relay buffers, half-close, idle timeouts, UDP session expiry, accept-loop
  backoff on EMFILE, handshake timeouts around TLS/REALITY (slow-loris).

### Net / DNS / routing / config
- DNS: TTL cache with negative caching, in-flight coalescing, UDP retransmit,
  answer/question matching, pooled DoT/DoH/DoQ connections.
- Router matchers, share-link parsing robustness.

### TUN / mobile / CLI
- Per-packet allocations removed, framed reads with `readv`/`writev`, the
  bridge survives a malformed packet, teardown registered with the panic hook
  (the release profile is `panic = "abort"`, so `Drop` never runs on panic).

### Scanner (`zero-scanner`)
- Scans that never ended, DPI check that failed every healthy IP, broken
  WebSocket/Trojan validation, wrong speed results, IPv6 ranges escaping
  their prefix, `/0` crash, unbounded memory, TUI terminal restore.

### TUI (`zeronet-tui`)
- **Stale cells on screen.** `☵` is two columns wide in terminals that follow
  Unicode 16, one in ratatui's table; every redraw of that row drifted. Test
  forbids glyphs whose width changed.
- **Animations froze on an in-between frame.** The frame after motion stops
  was never drawn. The loop now draws one settling frame.
- UI thread no longer blocks on system-proxy changes, sudo checks, TUN helper,
  database writes. Cleanup runs on every exit path and every signal; the
  proxy snapshot survives a crash and is restored on next launch.
- `/tmp` handover directory could be pre-owned by another local user.
- Settings saves no longer fail silently; the Feedback button was a
  placeholder and now copies a bug report.

## New in the TUI
- **Activity page** (key `5`): this app's CPU and memory with history, the
  machine's CPU and memory, a ranking against every running app, and the app
  list with this app's row always visible. Sampling runs on its own thread and

## TUN memory growth and config switching (follow-up)

Reported: memory climbing past 500-800 MB with TUN on, and TUN failing when
switching configs. Reproduced in an unprivileged user+network namespace with
a real TUN device, the real engine, and 300 concurrent TCP clients per burst.

| 300 connections through TUN, per burst | Before | After |
|---|---|---|
| Peak with all 300 open | 219 MB | 80-100 MB |
| After 6 bursts | 644 MB, still climbing | 88 MB, flat from burst 3 |
| Aggregate throughput | 2.9 Gbit/s | 2.8 Gbit/s |

Causes, all fixed:

1. **Routing loop in TUN mode.** Only proxy servers got bypass routes, so any
   connection the engine made directly (a `direct` rule, LAN, DNS) followed
   the default routes back into the tunnel and looped: thousands of
   connections a minute. Outbound sockets are now pinned to the physical
   uplink (`zero_core::platform::set_bound_interface`, `SO_BINDTODEVICE` /
   `IP_BOUND_IF`) while TUN is up.
2. **1.3 MB per TCP flow.** netstack-smoltcp's default buffers. Now 64 KiB
   socket buffers and half-size staging rings (vendored, `vendor/netstack-smoltcp`).
3. **Duplicate sockets from retransmitted SYNs**, and **orphaned connections
   kept for two hours**; `poll_shutdown` never completed a half-close. See
   `vendor/netstack-smoltcp/PATCHES.md`.
4. **Half-closed flows held for 5 minutes.** The relay now closes the other
   direction after 1 s of silence once one side finished (Xray's
   `uplinkOnly`/`downlinkOnly`), and frees the finished side's buffer early.
5. **Allocator retention.** glibc's arenas kept each burst's peak; the
   binaries now pin the mmap threshold at 64 KiB and use one arena.
6. **Config switch with TUN on.** The new helper tried to create the device
   while the old engine still held it (`EBUSY`). The helper and device are now
   kept across switches: only the bypass route is swapped (the helper learned a
   route-update command) and the next engine gets a fresh descriptor.
   Covered by `tun_handover::switching_servers_reroutes_the_bypass_without_rebuilding_the_interface`
   and verified end to end in the TUI: 20 switches, TUN stays up, 25 fds, flat memory.

## Xray compatibility fixes (the 14-bug report)

Each fix was checked against real Xray 26.7.28 servers: the local oracle
where a public server was not needed, the report's servers otherwise.

| # | Bug | Fix | Verified |
|---|---|---|---|
| 01 | XHTTP `extra` fields ignored | `extra` parsed from links and JSON (Xray's `SplitHTTPConfig.Build` rules and defaults). Requests shaped as Xray 26 shapes them: path normalisation, `x_padding` (Referer or obfuscated header/cookie/query, `repeat-x`/`tokenish` by HPACK length), session and sequence in path/header/cookie/query, packet data in body/header/cookie, Chrome `fetch` headers | 25 mode × security × placement combinations against Xray; oracle test `xhttp_requests_match_the_oracle` |
| 02 | XHTTP over REALITY never connects | Same root cause: Xray 26 answers every XHTTP request without valid `x_padding` with 400. Also HTTP version chosen as Xray does (TLS without a single ALPN is HTTP/2) | REALITY × stream-one/stream-up/packet-up/auto, with and without obfuscation |
| 03 | SS2022 chacha20-poly1305 | New cipher | 11/15 field servers, as Xray |
| 04 | VLESS ML-KEM encryption | New `zero_protocol::vless_encryption`: native/xorpub/random, 1-RTT and 0-RTT tickets, X25519 and ML-KEM-768 key chains, padding, rekeying, Vision's direct-read switch under encryption. BLAKE3 derive-key with byte contexts written from the spec and checked against the crate | Every mode × RTT × key type, Vision over raw/WS/XHTTP, every transport; oracle test `vless_encryption_matches_the_oracle` |
| 05 | REALITY over gRPC | Allowed | Local Xray, three fingerprints |
| 06a/b, 07 | VMess `type`, `aid` | Read as Xray and v2rayN read them | Field servers |
| 08 | Non-UUID IDs | Xray's UUIDv5 mapping | Field servers; Xray's own vectors in tests |
| 09, 10, 11, 14 | Empty `fp`, `fp=unsafe`, name casing, `&amp;` | Accepted as Xray accepts them | Link acceptance ~100% of each file |
| 12 | Vision over non-raw transports | Allowed with VLESS Encryption (Xray's rule); without it the error now says why | Vision + encryption over WS and XHTTP against Xray |
| 13 | REALITY with ML-DSA-65 | Already correct; the report's server no longer answers Xray either | Local Xray with `mldsa65Seed`, with and without `pqv`, 7-byte shortId, raw and XHTTP |

Found on the way:
- Our XHTTP HTTP/1.1 client sent `Connection: keep-alive`; Go's server then
  closes a streaming request body once the response starts, so stream-one and
  stream-up over HTTP/1.1 died after the first bytes. Xray's client sends
  `Connection: close`; so does ours now.
- XHTTP packet-up over HTTP/2 opened a new TCP+TLS connection for every
  upload. Uploads now ride the download's connection, as Xray's do, and are
  batched per posting interval: about 257 Mbit/s locally, Xray's own ceiling
  for the default 1 MB / 30 ms, against about 35 Mbit/s before.
- Our XHTTP HTTP/2 server answered only the first request on a connection;
  it now serves every request (Xray clients multiplex them).
- Outbound setup had no deadline after the TCP dial, so a server that accepted
  and went quiet held a session forever. TLS/REALITY, transport and protocol
  handshakes now share a 30 s deadline.

## Left open, by decision
- Hysteria2/TUIC clients open one QUIC connection per stream. Pooling is the
  largest latency win left, but a pooled client hangs against a server running
  the old accept code, so rollout order has to be decided first.
- XHTTP packet-up uploads one POST at a time (Xray sends them concurrently).
- QUIC congestion control stays Cubic; quinn's BBR is still experimental.
- The scanner's DPI check adds a fixed 350 ms per try and is on by default.
