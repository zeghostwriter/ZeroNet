## 1. Protocol overview

REALITY is a TLS 1.3 handshake in which the client hides an authentication tag inside the
ClientHello's `legacy_session_id` field, and the server presents a **temporary,
per-process self-signed Ed25519 certificate** whose (fake) signature is an HMAC keyed with
a secret only client and REALITY server can derive. Everything else on the wire is a
genuine TLS 1.3 handshake generated by the REALITY server, deliberately shaped like the
handshake of the real target site (`dest`).

The REALITY server (`RL/tls.go:162 Server()`) on every connection:

1. Dials the real target (`config.Dest`, e.g. `example.com:443`) and **mirrors** the
   client's ClientHello bytes to it (`RL/tls.go:207-232` reads the ClientHello, then a
   second goroutine pipes target→client).
2. In parallel, tries to authenticate the ClientHello (§2–§4). If authentication fails,
   the TCP connection becomes a transparent pipe to the target — the client completes a
   real TLS handshake **with the real site** (§8).
3. If authentication succeeds, the server reads the target's ServerHello, validates its
   shape, then **takes over the handshake**: it writes the target's ServerHello back to
   the client with only the `key_share` bytes rewritten in place to the REALITY server's
   own fresh X25519 (or ML-KEM) public key (`RL/tls.go:363-372` validation,
   `RL/handshake_server_tls13.go:101-132` key-share rewrite, `RL/handshake_server_tls13.go:837-841`
   write of `hs.hello.original`). Because `serverShare.data` and `sessionId` alias the
   original wire buffer (cryptobyte slices), the in-place `copy()` mutations are visible
   in `hs.hello.original` when it is written/transcripted.
   The `session_id` echo is already correct: the target echoes the mirrored ClientHello's
   32-byte tag verbatim.
4. From then on the REALITY server generates EncryptedExtensions, the temp Certificate,
   CertificateVerify (Ed25519) and Finished itself; the TLS 1.3 traffic keys are derived
   from ECDHE between **client and REALITY server** (`RL/handshake_server_tls13.go:106-132`,
   `:851-857`). The target connection stays open only for cover/traffic mimicry.

Client-side, the whole thing is a stock TLS 1.3 client (uTLS in Xray) with two hooks:
(a) patch the session_id before sending, (b) verify the temp certificate HMAC in
`VerifyPeerCertificate`.

## 2. Session-id auth tag (`ClientHello.session_id`)

### 2.1 Which field

In the **ClientHello**, `legacy_session_id` (the field that a TLS 1.3 client in compat
mode fills with a random 32 bytes). RFC 8446 §4.1.2 allows the client to send an
arbitrary value here and requires the server to echo it — REALITY exploits exactly this.
The "TLS 1.3 requires empty legacy_session_id" rule applies to the *client checking the
server's echo* and to the *ServerHello's own session_id semantics*, not to the client's
ClientHello field. The server echoes the 32 bytes back in the ServerHello
(`RL/handshake_server_tls13.go:270`: `hs.hello.sessionId = hs.clientHello.sessionId`;
on the wire the echo comes from the target's ServerHello which echoed the mirrored
ClientHello), so standard TLS stacks see a valid echo.

**Byte offsets inside the ClientHello handshake message** (`Raw`/`original` includes the
4-byte handshake header; layout from `RL/handshake_messages.go:377-391` marshal and
`:418-425` unmarshal):

```
offset  0 : 0x01                 (handshake type ClientHello)
offset  1 : uint24 body length
offset  4 : 0x0303               (legacy_version)
offset  6 : random[32]           ← salt = random[0:20], nonce = random[20:32]
offset 38 : uint8 session_id length  (= 32)
offset 39 : session_id[32]       ← the REALITY auth tag lives here (Raw[39..71])
offset 71 : uint16 cipher_suites length ... then extensions
```

`XC/reality.go:142` hardcodes this: `copy(hello.Raw[39:], hello.SessionId) // the fixed
location of 'Session ID'`.

### 2.2 Plaintext embedded in the tag (16 bytes)

| Offset | Size | Content |
|--------|------|---------|
| 0 | 1 | client version major (Xray: `core.Version_x`) |
| 1 | 1 | client version minor (`core.Version_y`) |
| 2 | 1 | client version patch (`core.Version_z`) |
| 3 | 1 | reserved, must be `0x00` |
| 4 | 4 | Unix time in **seconds**, **big-endian** `uint32` |
| 8 | 8 | `shortId` (config value, see §2.5) |
| 16 | 16 | zero padding (plaintext is only the first 16 bytes) |

Bytes 16..32 of the session-id buffer are never used; the GCM ciphertext (16 B plaintext
+ 16 B tag = 32 B) occupies the whole field.

### 2.3 Exact computation (Go, Xray client — verbatim)

Notes that MUST be reproduced exactly:

* `aead.Seal(dst=SessionId[:0], nonce=Random[20:32], plaintext=SessionId[:16],
  aad=hello.Raw)` — the **AAD is the full ClientHello handshake message with the
  session_id bytes zeroed**: the `copy(hello.Raw[39:], hello.SessionId)` on the line
  above the version assignments zeroed `Raw[39..71]`, and `hello.SessionId[:16]`
  (plaintext) does not include the tag area, so at Seal time `Raw[39..71]` = 32 zero
  bytes. After Seal, the 32-byte ciphertext is copied back into `Raw[39..71]`; those
  final wire bytes are what goes into the transcript.
* `crypto.NewAesGcm` is plain `aes.NewCipher(key)` + `cipher.NewGCM(block)`
  (`Xray-core/common/crypto/aes.go:34-39`). With the 32-byte auth key this is
  **AES-256-GCM**, standard 12-byte nonce, 16-byte tag → 16-byte plaintext seals to
  exactly 32 bytes.
* The timestamp is `uint32(time.Now().Unix())` — seconds, big-endian (§2.2).

### 2.4 Exact computation (Rust, SHOES — verbatim)

Plaintext construction, `SHOES/reality/reality_auth.rs:206-216`:

```rust
/// Creates a REALITY SessionId (test helper)
fn create_session_id(version: [u8; 3], timestamp: u32, short_id: &[u8; 8]) -> [u8; 32] {
```

`encrypt_session_id` (`SHOES/reality/reality_auth.rs:129-158`) is AES-256-GCM

### 2.5 shortId encoding (config)

* Client config `shortId`: hex string, ≤ 16 hex chars, decoded into an 8-byte array
  **left-aligned, zero-filled on the right** (`XF/infra/conf/transport_security.go`:
  `config.ShortId = make([]byte, 8); hex.Decode(config.ShortId, []byte(c.ShortId))`).
  Empty string ⇒ 8 zero bytes (servers list an empty shortId as `""` in `shortIds`).
* Server config `shortIds`: same hex→8-byte rule; the server does an **exact 8-byte map
  lookup** (`RL/tls.go:270`).

## 3. Auth key derivation

```
shared  = X25519(client_ephemeral_private, server_static_public("pbk" config))   // 32 bytes
AuthKey = HKDF-SHA256( ikm = shared, salt = client_random[0..20], info = "REALITY" )  // 32 bytes OKM
```

* Hash: **SHA-256** for both extract and expand (one HKDF, not staged).
* Salt: the **first 20 bytes** of the ClientHello random (the same hello that carries the
  tag). Info: the literal 7 ASCII bytes `"REALITY"`. Output length: 32.
* Order of operations in the client: generate ephemeral key → put its public key in the
  ClientHello key_share → build the ClientHello (random known) → ECDH → HKDF → build
  session-id plaintext → AES-256-GCM seal (§2.3).
* The server computes the mirror image (`RL/tls.go:239-247`):

```go
if hs.c.AuthKey, err = curve25519.X25519(config.PrivateKey, peerPub); err != nil {
    break
}
if _, err = hkdf.New(sha256.New, hs.c.AuthKey, hs.clientHello.random[:20], []byte("REALITY")).Read(hs.c.AuthKey); err != nil {
    break
}
block, _ := aes.NewCipher(hs.c.AuthKey)
aead, _ := cipher.NewGCM(block)
```

(`hkdf.New(...).Read(AuthKey)` reads 32 bytes into the 32-byte slice.)

* The *same* AuthKey is later reused by the client to verify the server certificate (§6).

Rust, `SHOES/reality/reality_auth.rs:98-114`:

```rust
pub fn derive_auth_key(
    shared_secret: &[u8; 32],
    salt: &[u8],
    info: &[u8],
) -> Result<[u8; 32], CryptoError> {
    debug_assert_eq!(salt.len(), 20, "salt must be exactly 20 bytes");
    let salt = Salt::new(HKDF_SHA256, salt);
    let prk = salt.extract(shared_secret);
    let info_pieces = [info];
    let okm = prk
        .expand(&info_pieces, HKDF_SHA256)
        .map_err(|_| CryptoError::HkdfFailed)?;
    let mut auth_key = [0u8; 32];
    okm.fill(&mut auth_key)
        .map_err(|_| CryptoError::HkdfFailed)?;
    Ok(auth_key)
}
```

## 4. Server-side verification mirror (what must match byte-exactly)

Verbatim decision code, `RL/tls.go:207-278` (goroutine that reads the ClientHello):

```go
mutex.Lock()
hs.clientHello, _, err = hs.c.readClientHello(context.Background())
if copying || err != nil || hs.c.vers != VersionTLS13 || !config.ServerNames[hs.clientHello.serverName] {
    break
}
var peerPub, peerPub2 []byte
for _, keyShare := range hs.clientHello.keyShares {
    if keyShare.group == X25519MLKEM768 && len(keyShare.data) == mlkem.EncapsulationKeySize768+32 {
        if peerPub2 != nil {
            peerPub2 = nil // ensure fail
            break // ensure once
        }
        peerPub2 = keyShare.data[mlkem.EncapsulationKeySize768:]
        continue // fast continue
    }
    if keyShare.group == X25519 && len(keyShare.data) == 32 {
        if peerPub != nil {
            peerPub2 = nil // ensure fail
            break // ensure once
        }
        peerPub = keyShare.data
        break // ensure order
    }
}
if peerPub2 == nil {
    break // reject outdated/strange Client Hello that doesn't have X25519MLKEM768 before optional X25519
}
if peerPub == nil {
    peerPub = peerPub2 // secondary choice: X25519 in X25519MLKEM768
}
for peerPub != nil {
    if hs.c.AuthKey, err = curve25519.X25519(config.PrivateKey, peerPub); err != nil {
        break
    }
    if _, err = hkdf.New(sha256.New, hs.c.AuthKey, hs.clientHello.random[:20], []byte("REALITY")).Read(hs.c.AuthKey); err != nil {
        break
    }
    block, _ := aes.NewCipher(hs.c.AuthKey)
    aead, _ := cipher.NewGCM(block)
    if config.Show {
        fmt.Printf("REALITY remoteAddr: %v\ths.c.AuthKey[:16]: %v\tAEAD: %T\n", remoteAddr, hs.c.AuthKey[:16], aead)
    }
    ciphertext := make([]byte, 32)
    plainText := make([]byte, 32)
    copy(ciphertext, hs.clientHello.sessionId)
    copy(hs.clientHello.sessionId, plainText) // hs.clientHello.sessionId points to hs.clientHello.raw[39:]
    if _, err = aead.Open(plainText[:0], hs.clientHello.random[20:], ciphertext, hs.clientHello.original); err != nil {
        break
    }
    copy(hs.clientHello.sessionId, ciphertext)
    copy(hs.c.ClientVer[:], plainText)
    hs.c.ClientTime = time.Unix(int64(binary.BigEndian.Uint32(plainText[4:])), 0)
    copy(hs.c.ClientShortId[:], plainText[8:])
    if config.Show {
        fmt.Printf("REALITY remoteAddr: %v\ths.c.ClientVer: %v\n", remoteAddr, hs.c.ClientVer)
        fmt.Printf("REALITY remoteAddr: %v\ths.c.ClientTime: %v\n", remoteAddr, hs.c.ClientTime)
        fmt.Printf("REALITY remoteAddr: %v\ths.c.ClientShortId: %v\n", remoteAddr, hs.c.ClientShortId)
    }
    if (config.MinClientVer == nil || Value(hs.c.ClientVer[:]...) >= Value(config.MinClientVer...)) &&
        (config.MaxClientVer == nil || Value(hs.c.ClientVer[:]...) <= Value(config.MaxClientVer...)) &&
        (config.MaxTimeDiff == 0 || time.Since(hs.c.ClientTime).Abs() <= config.MaxTimeDiff) &&
        (config.ShortIds[hs.c.ClientShortId]) {
        hs.c.conn = conn
    }
    break

```

Checklist of what the server requires (all must hold, else the connection is silently
forwarded to `dest`):

1. **TLS 1.3 negotiated**: `hs.c.vers == 0x0304` (from `supported_versions`).
2. **SNI allowlist**: `config.ServerNames[serverName]` — exact string match against the
   server's `serverNames` list. Send SNI = the configured `serverName`.
3. **Key share rules** (current server, RL @ 5dabb07 / Xray ≥ v26.9.x):
   * An `X25519MLKEM768` (0x4588) key share of exactly **1184 + 32 = 1216 bytes** MUST be
     present (`mlkem.EncapsulationKeySize768 = 1184`).
   * It must appear **before** any optional `X25519` (0x001d) share. Each group may occur
     at most once (duplicates ⇒ reject).
   * The auth ECDH uses the standalone `X25519` share's bytes if present, otherwise the
     **last 32 bytes** of the X25519MLKEM768 share (`data[1184..1216]`).
   * *v26.3.27-era servers* (reality ≤ 2026-03-22): no MLKEM requirement; a standalone
     `X25519` share alone is sufficient; the MLKEM X25519-component fallback (added
     2025-07-22) applies otherwise. See §7.2.
4. **Session-id decryption**: AES-256-GCM open with `key = AuthKey`,
   `nonce = client_random[20..32]`, `aad = full ClientHello handshake message with
   session_id zeroed`. Note the server zeroes the session_id **in place** before `Open`
   — `hs.clientHello.sessionId` aliases `original[39..71]` (cryptobyte subslice), so
   `hs.clientHello.original` at Open time is the wire hello with bytes 39..71 zeroed.
   That is byte-identical to what the client used as AAD (§2.3).
5. **Version gate**: decrypted `ClientVer = plain[0..4]` compared numerically (big-endian,
   `Value()` at `RL/tls.go:153-158`) against `minClientVer`/`maxClientVer` (3-byte
   arrays). `nil` config ⇒ no gate. See §10.
6. **Time window**: `ClientTime = Unix(BigEndian.Uint32(plain[4..8]))`. If
   `maxTimeDiff != 0` (config, **milliseconds**): `|now − ClientTime| ≤ maxTimeDiff`
   (symmetric, `time.Since(...).Abs()`). If `maxTimeDiff == 0`: **no time check at all**
   (Xray default; the JSON field is optional, `XF/infra/conf/transport_security.go:152`).
   Common production value: 60000 ms (±60 s).
7. **shortId**: `plain[8..16]` must be an exact member of the server's
   `map[[8]byte]bool` (`config.ShortIds`). No prefixes/windows — full 8-byte equality.
8. **No replay cache.** Current REALITY keeps no per-session-id replay memory
   (`RL/cache.go` is only an x509 parse cache). A replayed ClientHello within the time
   window will authenticate again. Replay resistance comes solely from the time window
   (and, if unset, nothing).

Success is expressed as `hs.c.conn = conn` — one pointer assignment. Everything else
continues down the fallback path (§8).

## 5. ServerHello — what the client receives and how "REALITY" is confirmed

**There is no authentication in `ServerHello.random` in the current protocol.** The
random the client sees is the **real target site's random**, untouched
(`RL/handshake_server_tls13.go` `processClientHello` — which would have generated a fresh
random — is commented out; `hs.hello` is unmarshaled from the target's bytes at
`RL/tls.go:364-371`). The rustls-reality fork's `inject_auth` scheme
(`rustls-reality/rustls/src/reality.rs:49-71`, HMAC into `random[20..32]`) is **not**
XTLS REALITY; do not implement or expect it.

What the server actually sends as ServerHello (all derived from the target's ServerHello,
`RL/tls.go:363-371` + `RL/handshake_server_tls13.go:837-841,101-132`):

* `legacy_version` = 0x0303, `supported_versions` ext = 0x0304 (validated on the target's
  hello before it is accepted).
* `random` = target's random, unchanged.
* `session_id` = exact echo of our 32-byte tag (target echoed the mirrored ClientHello).
* `cipher_suite` = the target's choice (must be a known TLS 1.3 suite: 0x1301/0x1302/0x1303).
* `key_share` = **rewritten in place** to the REALITY server's freshly generated key:
  * if target chose X25519 (0x001d): the server's new 32-byte X25519 public key;
  * if target chose X25519MLKEM768 (0x4588): `ML-KEM-768 ciphertext (1088 B) || server's
    new X25519 public key (32 B)` (total 1120 B ciphertext-share; server does the
    encapsulation itself, `RL/handshake_server_tls13.go:124-129`).
* No HelloRetryRequest path: if the target sends HRR/TLS1.2/garbage, the REALITY server
  switches to transparent forwarding of the target's bytes (`RL/tls.go:443-457`).

Consequently the **client-side confirmation that the peer is REALITY is the temporary
certificate (§6)** — not any ServerHello bytes. The client's TLS stack processes the
ServerHello like any TLS 1.3 handshake: the transcript is
`ClientHello(wire bytes, tag included) || ServerHello(received bytes)`, and the shared
secret for the TLS key schedule is ECDH between the client's key-share secret and the
server's key share **from the received ServerHello** (X25519 or ML-KEM hybrid).

Client-side ServerHello parsing requirements (minimal client):
* extract server key_share (X25519 32 B, or X25519MLKEM768 1120 B = 1088 ct + 32 x25519),
* extract cipher suite (restrict to what you implement; SHOES offers/accepts TLS1.3
  suites only, `SHOES/reality/reality_cipher_suite.rs`),
* verify (implicitly, via the standard TLS 1.3 stack) that `ServerHello.session_id`
  equals the 32 bytes we sent,
* skip the dummy ChangeCipherSpec record that follows (`RL/handshake_server_tls13.go:844`
  `sendDummyChangeCipherSpec`; SHOES skips CCS at
  `reality_client_connection.rs:530-537`).

## 6. Temporary certificate verification (client side)

### 6.1 What the server sends

Server-global, per-process material (`RL/handshake_server_tls13.go:74-86`):

(`joint-iso-itu-t(0) / 0`), containing 3309 zero bytes as a placeholder).

Interpretation (note the Go trick: `h.Sum(b)` returns `append(b, digest...)`; because
`cert` has spare capacity, the digest overwrites the last 64 bytes **in place**):

* **Certificate signature field** (last 64 bytes of the DER, the Ed25519 signature bit
  string) `:= HMAC-SHA512(key = AuthKey, message = ed25519_public_key(32 bytes))`.
  The certificate is therefore *not* a valid self-signature — by design.
* The Certificate message carries exactly this one certificate, no chain
  (`certificate_request_context` empty, one entry, empty entry extensions).
* **CertificateVerify**: a genuine TLS 1.3 signature, scheme `ed25519` (0x0807), over
  `64×0x20 || "TLS 1.3, server CertificateVerify" || 0x00 || transcript_hash`
  (`RL/auth.go:106-131` `signedMessage`; signing at
  `RL/handshake_server_tls13.go:958-976`). Any TLS 1.3 client verifies this against the
  leaf cert's Ed25519 public key as usual.
* **ML-DSA-65 extra signature (optional)**: the HMAC state continues —
  `h.Write(clientHello.original)`, `h.Write(serverHello.original)` (the raw handshake
  messages as on the wire, 4-byte headers included, record headers excluded) — and
  `h.Sum(nil)` = `HMAC-SHA512(AuthKey, ed25519_pub || ClientHello_wire || ServerHello_wire)`
  (64 bytes) is signed with **ML-DSA-65** (randomized signing, empty context). The
  signature (3309 bytes) is written into the certificate DER at **fixed byte offset 126**
  — i.e. into the value octets of the OID-0.0 extension of the template cert.

```rust
/// Verify the HMAC signature embedded in the REALITY certificate
///
/// In REALITY protocol, the server embeds HMAC-SHA512(auth_key, ed25519_public_key)
/// in the signature field of the certificate.
#[inline]
pub fn verify_certificate_hmac(cert_der: &[u8], auth_key: &[u8; 32]) -> io::Result<()> {
    let (_, cert) = X509Certificate::from_der(cert_der).map_err(|e| {
        io::Error::new(
            io::ErrorKind::InvalidData,
            format!("Failed to parse X.509 certificate: {}", e),
        )
    })?;

    let spki = cert.public_key();
    let pubkey_data: &[u8] = &spki.subject_public_key.data;
    let signature: &[u8] = &cert.signature_value.data;

    // Verify this is an Ed25519 public key (32 bytes)
    if pubkey_data.len() != 32 {
        return Err(io::Error::new(
            io::ErrorKind::InvalidData,
            format!(
                "Expected Ed25519 public key (32 bytes), got {} bytes",
                pubkey_data.len()
            ),
        ));
    }

    // Verify signature is exactly 64 bytes (HMAC-SHA512 output)
    if signature.len() != 64 {
        return Err(io::Error::new(
            io::ErrorKind::InvalidData,
            format!(
                "Expected 64-byte signature for HMAC-SHA512 verification, got {} bytes",
                signature.len()
            ),
        ));
    }

    // Compute expected HMAC: HMAC-SHA512(auth_key, ed25519_public_key)
    let hmac_key = hmac::Key::new(hmac::HMAC_SHA512, auth_key);
    let hmac_tag = hmac::sign(&hmac_key, pubkey_data);
    let expected_signature = hmac_tag.as_ref(); // Full 64 bytes

    // Compare full 64-byte signature with expected HMAC using constant-time comparison
    if expected_signature.ct_eq(signature).unwrap_u8() == 0 {
        // HMAC mismatch - the certificate is not signed by a REALITY server.
        return Err(io::Error::new(
            io::ErrorKind::PermissionDenied,
            "Certificate HMAC verification failed - not a REALITY-signed certificate",
        ));
    }

    Ok(())
}
```

## 7. ClientHello shape requirements

### 7.1 Mandatory content

1. **TLS 1.3 via `supported_versions` (0x002b)** — server rejects otherwise
   (`hs.c.vers != VersionTLS13` check, `RL/tls.go:211`). legacy_version field = 0x0303.
2. **key_share (0x0033) containing the REALITY auth share** — see §7.2 for the rules.
   The **secret of this share** must be the one used for the §3 ECDH. Xray picks
   `State13.KeyShareKeys.Ecdhe` (standalone X25519 secret), falling back to
   `KeyShareKeys.MlkemEcdhe` (the X25519 component secret of the X25519MLKEM768 hybrid)
   (`XC/reality.go:156-159`). If neither exists → **hard client-side error**
   `"Current fingerprint ... does not support TLS 1.3, REALITY handshake cannot
   establish."` (`XC/reality.go:160-162`). There is no client-side retry/fallback.
3. **`session_id` = exactly 32 bytes** carrying the §2 tag (single session-id entry; the
   length byte at offset 38 must be 32 so offset 39 is right).
4. **SNI (0x0000) = `serverName`** from config — must match the server's `serverNames`
   allowlist exactly (`RL/tls.go:211`). Xray falls back to the dial address if
   `serverName` is empty (`XC/reality.go:129-131`).
5. **Fingerprint profile**: Xray uses uTLS; default fingerprint `chrome`
   (`utls.HelloChrome_Auto`, `XF/tls/tls.go:187-201`). Any profile works cryptographically
   as long as it yields a TLS 1.3 hello with a usable x25519(-in-hybrid) key share.
   `unsafe` / `hellogolang` are rejected in client config parsing
   (`XF/infra/conf/transport_security.go`).
6. **ALPN**: Xray's REALITY `UClient` sets no `NextProtos` on the uTLS config
   (`XC/reality.go:122-128`), so the hello carries the fingerprint's default ALPN —
   Chrome profiles send `["h2", "http/1.1"]`. SHOES hardcodes
   `DEFAULT_ALPN_PROTOCOLS = &["h2", "http/1.1"]`
   (`SHOES/reality/reality_tls13_messages.rs:259-260`). The REALITY server has
   `NextProtos: nil` (`XCC/config.go:31`), so `negotiateALPN` returns "" and the
   EncryptedExtensions contain **no ALPN extension** (`RL/handshake_server.go:336-343`) —
   the client must tolerate that.
7. **Session resumption must be off**: `SessionTicketsDisabled: true` and no
   `ClientSessionCache` (`XC/reality.go:126`). A PSK resumption would omit the ECDHE
   share and break both auth and the server's flow. (The server also ignores/handles
   PSK hellos only via fallback.)
8. **compression methods** = `[0x00]` (single null; server rejects others,
   `RL/handshake_server_tls13.go:237-241`).
9. No empty renegotiation_info, no early_data. If you send a PSK extension you must send
   valid binders (simpler: don't send PSK at all).
10. A minimal known-good extension set (SHOES, in this order):
    `server_name(0)`, `supported_versions(43)`, `supported_groups(10)`, `key_share(51)`,
    `signature_algorithms(13)` = `[0x0403,0x0804,0x0401,0x0503,0x0805,0x0501,0x0806,0x0601]`
    (Chrome 133 set), `alpn(16)`.
    (`SHOES/reality/reality_tls13_messages.rs:273-414`.)

### 7.2 Key-share group rules by server version (decides your supported_groups + key_share lists)

| Server | X25519MLKEM768 share | standalone X25519 share | auth ECDH share used |
|---|---|---|---|
| ≤ v26.9.8 (reality < 8cdf7bf), incl. **v26.3.27** | optional | optional | standalone X25519 if present, else X25519 component (last 32 B) of MLKEM share |
| ≥ v26.9.9 (reality 8cdf7bf / 5dabb07) | **required, must precede any X25519** | optional, at most once | standalone X25519 if present, else MLKEM X25519 component |

* Chrome-like order `X25519MLKEM768, X25519` satisfies both versions.
* X25519-only (SHOES style) works on ≤ v26.9.8 and is **silently forwarded to the
  fallback site** on ≥ v26.9.9 (your cert-HMAC check then fails → §8).
* Duplicate shares of either group ⇒ reject on the new server.
* The ClientHello that failed this check is never authenticated, regardless of a valid tag.

### 7.3 Where each byte comes from (order of operations, client)

1. Generate ephemeral X25519 (or Chrome-style hybrid) keypair.
2. Build the full ClientHello (with a placeholder/zero session_id — it will be replaced;
   only the *length* (32) matters for offsets).
3. `shared = X25519(ephemeral_secret, pbk)`; `AuthKey = HKDF(...)` (§3).
4. Build the 16-byte plaintext (§2.2), AES-256-GCM seal with `nonce = random[20..32]`,
   `aad = hello_with_zeroed_session_id`, write the 32-byte output into `hello[39..71]`.
5. The bytes you now have are both the wire hello and the transcript hello
   (`SHOES/reality/reality_client_connection.rs:1022-1054` test).

## 8. Fallback path (server rejects / proxies to the real site)

If any §4 check fails, the REALITY server never writes its own handshake; the TCP stream
becomes a direct pipe client↔`dest` (`RL/tls.go:281-296` upload side, `:443-457`
download side, with optional rate limiting). From the client's view:

* The TLS handshake **completes** — against the *real target site's* ServerHello and its
  genuine certificate chain. Because the client sets `InsecureSkipVerify: true`
  (`XC/reality.go:125`), the handshake itself will not fail on the strange chain
  *unless* the chain doesn't validate at all (see below).
* Xray/sing-box detect fallback **only** through `VerifyPeerCertificate` (§6.2):
  the leaf cert of a real site is rarely Ed25519, and even if it were, the
  `HMAC-SHA512(AuthKey, pub) == cert.Signature` check fails (the attacker/server cannot
  produce it without AuthKey). When the HMAC fails, the callback falls through to a
  **real X.509 verification** of the presented chain (`DNSName = serverName`,
  intermediates = rest of chain):
  * If the real site's chain validates → callback returns `nil` (no TLS error!), the
    handshake finishes, and the caller checks the `Verified` flag.
  * If it does not validate → `certs[0].Verify` errors → the TLS handshake fails with an
    error. (This is also what a MITM that re-terminates TLS would hit.)
* After a completed handshake with `Verified == false`, Xray
  (`XC/reality.go:183-275`):
  1. logs `"REALITY: received real certificate (potential MITM or redirection)"`;
  2. spawns the **spider**: an HTTP/2 client over the *same* connection crawls the real
     site (starting at `spiderX`, following `href` links, random Referer chain,
     `padding` cookies of random length, randomized counts/intervals from `spiderY`),
     mimicking a browser that connected to the wrong vhost — this feeds realistic
     traffic to any observer;
  3. sleeps a random `spiderY[8..9]` ms, then returns
     `"REALITY: processed invalid connection"` (warning). The proxy request fails; the
     client should retry a new connection.
  sing-box does a simpler variant: one `GET https://serverName` with a random
  `padding` cookie, then error (`SB/reality_client.go:236-266`).
  SHOES has no spider: HMAC mismatch is a hard error
  (`SHOES/reality/reality_client_verify.rs:152-167`).
* Another fallback trigger that is *not* visible as a cert failure: if the target site
  answers with TLS ≤ 1.2, an HRR, or an unexpected ServerHello, the REALITY server just
  pipes the target's bytes (`RL/tls.go:332-345, 443-457`). The client then sees a
  non-TLS1.3 ServerHello or HRR — a TLS 1.3-only client should treat that as
  handshake failure (and can retry); Xray's uTLS would follow the HRR, complete against
  the target, and then fail the HMAC check as above.

Practical rule for our client: after the handshake completes, **treat the connection as
REALITY only if the cert HMAC (and CertificateVerify) verified**; otherwise discard the
connection (optionally after mimicking some browsing traffic) and retry.

## 9. Post-handshake data plane

* After Finished, the connection is a **completely standard TLS 1.3 record layer**:
  AES-128/256-GCM or ChaCha20-Poly1305 per the negotiated suite, sequence numbers from
  0, nonce = static IV XOR seq (big-endian, per RFC 8446 §5.3). Application data flows
  directly between client and REALITY server (the server sets `hs.c.conn = conn` and
  Xray proxy layers take over). **No extra REALITY framing, no extra headers.**
* Traffic keys come from the key schedule of the handshake the client actually
  observed (transcript over wire bytes; ECDHE vs the REALITY server's key share in the
  modified ServerHello). Standard TLS 1.3 `KeyUpdate` (0x18) applies and must be
  supported (Go stack implements it; SHOES tolerates/handles records via its decryptor).
* Server-side mimicry you may *observe* (be tolerant):
  * a dummy plaintext `ChangeCipherSpec` record right after ServerHello
    (`RL/handshake_server_tls13.go:844`);
  * after the handshake, the server may send **fabricated application-data records**
    whose lengths replicate the target site's post-handshake records (session tickets),
    contents decrypting to content-type 0x17 with an all-zero (empty) payload —
    `RL/tls.go:405-438`. Zero-payload app-data records are legal; just ignore them.
  * `MaxUselessRecords` (tolerated CCS/garbage records count) is tuned to the target's
    behavior (`RL/tls.go:435-437`) — don't hard-fail on stray CCS records.
* Close: normal TLS 1.3 `close_notify` handling.

## 10. ML-DSA-65 extra signature & version gating (`minClientVer` etc.)

**ML-DSA-65** (optional hardening, both sides must opt in):
* Server config `mldsa65Seed` (base64 RawURL, 32 B) → server signs (§6.1) and uses the
  cert template with the OID-0.0 extension (`XCC/config.go:36-39`).
* Client config `mldsa65Verify` (base64 RawURL, **1952 bytes** = ML-DSA-65 public key,
  `XF/infra/conf/transport_security.go`) → after the HMAC match, continue the HMAC with
  `ClientHello.Raw || ServerHello.Raw`, verify ML-DSA-65 over the 64-byte digest against
  the signature found in `certs[0].Extensions[0].Value` (§6.2).
* If the client requires ML-DSA but the cert has no extensions, verification fails and
  the client falls to X.509 verification → handshake error. If the server uses ML-DSA
  but the client doesn't configure it, the client simply ignores the extension.
* The ML-DSA verify input is the **HMAC digest itself** (64 B), signed in ML-DSA pure
  mode, empty context; randomized signatures (so it changes per connection).

**Version gating**:
* The 4 decrypted bytes `plain[0..4]` are compared against the server's
  `minClientVer`/`maxClientVer` (each an optional 3-byte array parsed from dotted
  decimal) as big-endian integers with zero bytes appended (`Value()`,
  `RL/tls.go:153-158`; comparison `RL/tls.go:267-269`). Byte 3 of the plaintext
  participates but is always 0.
* Default server config: **no gate** (`minClientVer` unset ⇒ `nil` ⇒ check skipped).
  Xray's source carries a commented-out default of `[]byte{26, 3, 27}`
  (`XF/infra/conf/transport_security.go`, "change it at your own risk") — server
  operators may enable it to refuse clients that claim a version below Xray-core
  v26.3.27 (the release whose client emits modern, MLKEM-bearing ClientHellos).
* The client **always** embeds a version — there is no negotiation or explicit signaling
  beyond these three bytes. Xray embeds its real core version (`core.Version_x/y/z`,
  `XC/reality.go:143-145`). sing-box embeds the constant `1.8.1` (`SB/reality_client.go:186-188`)
  — which would **fail** a server gated at `minClientVer=26.3.27` (1 < 26).
* **Recommendation for our client**: embed `[26, 3, 27]` (or our emulated Xray version if
  ≥ 26.3.27) with reserved byte 0, so we pass any `minClientVer` gate that targets
  Xray ≥ v26.3.27, and set the timestamp from a clock we keep within ±`maxTimeDiff`
  (enable NTP or derive from responses; default servers don't check time).

**Config encodings recap** (for share-links / UI parity):
`publicKey`/`password` = base64 **RawURL** (no padding), 32 B; `shortId` = hex ≤ 16 chars
→ 8 B right-padded with zeros; `mldsa65Verify` = base64 RawURL, 1952 B
(`XF/infra/conf/transport_security.go`).

## 11. Implementation checklist / gotchas

1. AAD for session-id encryption = ClientHello with bytes `[39..71]` **zeroed**;
   transcript/`CertificateVerify`/ML-DSA HMAC use the ClientHello with the **ciphertext**
   in `[39..71]` (the wire bytes).
2. `salt = random[0..20]`, `nonce = random[20..32]` — both from the *final* hello random
   (which never changes after hello construction).
3. shortId must be the full 8 bytes; hex strings are right-padded with zeros.
4. Timestamp: seconds, `u32`, big-endian; watch for 2038-overflow (wraps, like Go).
5. Constant-time compare the 64-byte cert HMAC (`subtle::ConstantTimeEq`).
6. Verify order: parse leaf DER → Ed25519 pubkey (32 B) → HMAC → (optional ML-DSA) →
   CertificateVerify (Ed25519, RFC 8446 §4.4.3 framing) → Finished.
7. The ServerHello may select either X25519 or X25519MLKEM768; the TLS key schedule
   must handle both if you offer both groups. The REALITY auth share is *independent*
   of which group the ServerHello selects.
8. Skip the dummy CCS record after ServerHello; tolerate zero-payload app-data records
   post-handshake.
9. No ALPN in EncryptedExtensions even if you offered ALPN.
10. On HMAC failure: fallback happened — abort (or spider), never send proxy data into
    the fallback connection.
11. Transcript hashing starts with the full wire ClientHello handshake message
    (including its 4-byte header), then every received handshake message plaintext
    (4-byte header + body), in order: ServerHello, EncryptedExtensions, Certificate,
    CertificateVerify; client Finished verifies with `finished_mac =
    HMAC(finished_key, Hash(transcript || server_msgs))` per RFC 8446 (finished_key =
    HKDF-Expand-Label(client_handshake_traffic_secret, "finished", "", hash.len)).
12. Record layer: TLS 1.3 AEAD, seq starts at 0 per direction per key epoch; treat
    handshake-phase and application-phase keys as separate epochs with separate seqs.
